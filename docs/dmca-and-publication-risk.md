## DMCA 是什么

DMCA 全称 Digital Millennium Copyright Act，中文通常称美国《数字千年版权法》。本项目尤其需要区分两个问题：

- **版权通知与下架**：第 512 条涉及平台安全港及通知处理机制；平台限制访问并不是法院对侵权作出最终判决。见[美国版权局第 512 条说明](https://www.copyright.gov/512/)。
- **反规避**：第 1201 条涉及规避有效控制受版权保护作品访问的技术措施，以及提供某些规避技术、产品或服务。它不只是“有没有复制别人的源代码”的问题。见[第 1201 条](https://www.law.cornell.edu/uscode/text/17/1201)。

已公开的 wx-cli 与 wechat-decrypt 通知中，投诉方主张密钥提取和数据库解密绕过了对其数据库设计的保护，并提出相关合同和平台政策主张。这是投诉方的法律观点；本文不据此认定全部表结构当然享有版权、解密自己数据当然违法，或相关主张已经获得法院支持。[wx-cli 通知](https://github.com/github/dmca/blob/master/2026/07/2026-07-13-wechat.md)、[wechat-decrypt 通知](https://github.com/github/dmca/blob/master/2026/07/2026-07-13-wechat-3.md)。

## 本仓库的风险判断

**工程层面的判断是：本项目存在实质性的投诉与下架风险。** 依据是本地源码包含 Windows 密钥扫描与账号捕获、数据库解密，以及所涉上游能力的移植；这些能力与公开通知涉及的技术范围相近。这是风险推断，不是违法认定，也不表示已经核实本仓库收到通知。

Apache-2.0、MIT 等许可证处理的是相应贡献者能够授权的权利，不能自动代替其他权利人的授权。Rust 重写和独立实现可能改变复制关系，但不会单独消除关于技术规避行为的争议。“个人数据”“教育研究”也不能单独替代对第 1201 条适用条件及例外的分析。

GitHub 不会仅因父仓库被禁用就自动禁用所有 fork，但其政策允许在符合条件的投诉中处理整个大型 fork 网络。因此，另建仓库或脱离 fork 关系不能作为无风险保证；当前是否可访问也不是法律结论。[GitHub 对 fork 的政策](https://docs.github.com/en/site-policy/content-removal-policies/dmca-takedown-policy#b-what-about-forks-or-whats-a-fork)。

## 下架是否会影响技术文档

### 同仓库的可用性

如果整个仓库被禁用，同仓库文档也会失去公开访问入口，即使其中某些文件并未单独被指控。GitHub 的政策说明其不能在仓库中仅禁用特定文件；“文档没有可执行代码”不能保证它在整库处理时仍可访问。[GitHub 下架流程](https://docs.github.com/en/site-policy/content-removal-policies/dmca-takedown-policy#a-how-does-this-actually-work)。

### 独立文档的内容风险

| 内容 | 应如何评估 |
| --- | --- |
| 本项目业务模型、模块职责、任务调度和通用设计 | 与微信保护措施规避的关系通常更弱，但仍需确认没有未经许可的复制内容。 |
| 用原创文字描述数据格式、字段语义和互操作接口 | 原理、方法与具体表达需要区分。美国版权法第 102(b) 条不把思想、过程、系统、操作方法或原理本身纳入版权保护；不能据此推导任何逆向获取方式或发布方式都不受限制。 |
| 指定版本的完整密钥捕获步骤、Hook 实现、可直接重建解密工具的伪代码与参数 | 与已有反规避投诉更接近，应针对具体内容与用途评估；文件格式或语言不会自动消除风险。 |
| 复制的代码、反编译片段、WASM 和其他第三方资产 | 还需审查具体表达与资产的许可；改成文档附件不会改变来源。 |

上述是评估方向，不是“前两类一定安全、后两类一定违法”的法律分级。[美国版权法第 102(b) 条](https://www.copyright.gov/title17/92chap1.html#102)。

第 1201(f) 条为特定互操作逆向及相关信息、手段的提供设置了有条件的例外，其他研究例外也有各自限制。不能仅给项目贴上“互操作”或“研究”标签就认定适用，也不能把允许某项研究行为直接等同于允许公开分发所有工具。[第 1201(f)、(g) 条](https://www.law.cornell.edu/uscode/text/17/1201)。

将文档放到独立位置，可以在技术上降低同一仓库被禁用带来的连带不可用，但不会产生法律豁免。是否能继续发布取决于文档内容、具体通知、适用法律和可能的法院命令，而非仅取决于是否存放在代码仓库。

## 是否拆分代码仓库与机制文档仓库

可以采用两个仓库：代码仓库保存程序、使用指南和 wx-cli 架构说明；机制文档仓库保存按微信版本组织的事实描述、数据模型、字段语义、接口约定、验证方法和合成样例。前者回答“这个程序如何实现”，后者回答“已观察到的数据机制是什么”。机制文档应独立可读，不依赖代码仓库链接才能理解关键定义。

这种拆分有维护与可用性价值：代码仓库被停用时，独立文档仓库不会仅因处于同一个仓库中而一起失去入口。但文档仓库仍可能被单独或同时投诉；不能将拆分视为法律隔离，也不应把它用作重发已被投诉内容的安排。

没有足够的可比统计支持“纯文档被 DMCA 的概率很低”。作为内容层面的风险判断，原创的一般机制与互操作说明通常比密钥提取、数据库解密工具更远离本次公开通知的直接指控；若文档包含同等可操作的捕获步骤、解密伪代码或相关资产，则不能仅因没有可执行文件就作同样判断。这一比较不构成概率估计或合法性结论。

两个仓库可以先按各自目的完整编写和维护，再对拟公开内容分别审查。文档可支持独立实现的目标，仍需受到具体内容、适用法律与例外条件的约束；仓库结构本身不能解决这些问题。

## 文档建设与通知处理

本项目继续以保存可验证的技术知识、支持合法的独立实现为文档目标，但不承诺所有机制都能无限制公开。文档应标注微信版本、证据来源、验证范围和第三方归属，使用合成样例，并将一般机制描述与可能涉及保护措施规避的实现说明分别审查。

收到通知时，应保存通知与相关版本记录、确认被指控的具体内容，并在平台期限内结合专业法律意见回应。反规避投诉有 GitHub 专门的技术与法律审查流程；反通知不是无风险的恢复按钮。不应把换地址、换格式或继续发布等效内容视为已经解决争议。[GitHub 反规避投诉流程](https://docs.github.com/en/site-policy/content-removal-policies/dmca-takedown-policy#c-what-about-circumvention-claims)。

因此，“源码失去可用性后仍能依据文档独立实现”是知识保存目标；“源码被 DMCA 处理后文档一定可以继续公开”不是本项目能够作出的保证。
