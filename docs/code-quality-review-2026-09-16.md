# wx-workbench 改名与代码质量修订

本轮从 `445d64b` 开始，验收前快进合入另一个任务已提交的 `d4e22a0`，最终检查针对两部分合并后的工作区。覆盖项目名称、第一方 Rust 代码与测试、独立夹具，以及仓库内 Python/JavaScript 文件的语法检查。保留此前的 README 和文档修订；没有改写历史审查报告或第三方来源记录。

## 项目名称

产品改名为 **wx-workbench（微信本地数据工作台）**。当前系统已有 CLI、MCP、本地 Web、账号 daemon、归档和媒体处理，`wx-cli` 不再充分表达产品范围。

更新 Cargo 包、npm 包与平台依赖、安装器、发布工作流、MCP 展示名称、CLI 帮助、Web 标题、仓库技能及当前说明。正式命令仍为 `wx`；发布清理移除 `wx-toolbox` binary、npm 旧覆盖变量及旧附件/安装目录回退。运行时环境变量、账号目录和 IPC/磁盘标识不在该发布清理范围，真实用户文件不自动搬迁或删除。来源仓库仍使用原名。具体映射及外部发布步骤见[当前命名与发布说明](project-naming.md)。

GitHub 仓库已更名为 `leyan2174/wx-workbench`，新地址及 main 引用已核验，本 checkout 的 origin 已同步。npm 包名已在源码更新，但尚未发布。本轮没有提交或推送这些修订、发布包或创建版本。

另一个任务的 P1 修复涉及 Windows 伪环境变量、稳定 username 的账号内证据匹配和查询预算诊断，具体见 [P1 修复说明](export-p1-fixes.md)。合并保留 history 专门的预算错误映射，不经过普通字符串响应包装；清理器采用该提交可测试的退出查询函数，并保留有界退出等待。这些 P1 功能不计为本轮改名与抽象整理的原创变更。

## 已完成的结构整理

| 位置 | 问题 | 修订 |
| --- | --- | --- |
| daemon 请求分发 | 重复的成功/错误包装混在路由中 | 相同转换共用 `Response::from_result`；语音、图片的错误隐藏策略和 history 预算错误映射单独保留 |
| 消息存储读取接口 | 搜索关键词与预览解码器是两个独立可选参数 | 用 `LegacySearch` 将二者绑定，减少无效参数组合与复杂回调签名 |
| 语音导出 | 时间、分页等筛选项散列为函数参数 | 复用已有业务 `Selection`，不新建重复筛选模型 |
| 引用消息与导出上下文 | 枚举大小由少数大分支决定 | 对大型数据成员使用 `Box`，保持公开数据投影不变 |
| 消息监控 | 游标公开规则嵌在深层分支内 | 提取状态生成步骤；不完整批次仍不提交新游标，错误重试仍遵守等待间隔 |
| 延迟监测 | 文件观察与 IPC 探测状态交织 | `SourceObserver` 负责文件变化观察、耗时和未确认变化；探测循环保留原有测量边界 |
| 朋友圈发布 | 名称、路径验证夹在发布大函数中 | 提取整批预检；所有联系人仍先完成预检，再执行发布 |
| npm 启动器 | 二次路径解析重复，平台包缺失时可能抛出内部异常 | 简化为一次解析和明确安装提示；验证新旧二进制覆盖变量的优先级 |

此外，清理多余借用、无必要克隆、冗余转换、测试模块位置与失效的 lint expectation；修正测试中未检查网络读取长度的问题。没有通过 crate 级关闭告警来获得通过结果。

## 测试与维护机制

- 前端边界检查由字符串匹配改为与 daemon/service 检查共用的 Rust 语法树遍历，覆盖 CLI、Web、MCP。增加分组导入、重命名导入、通配导入、空白变化、注释和测试模块的反例。它仍是源码约束检查，不是编译器级名称解析或宏展开证明。
- 原生迁移安全测试复用生产级受管进程执行器：60 秒期限、8 MiB 输出预算和 Windows Job 后代回收。故意制造孤儿进程的生命周期样本在准确位置注明 Clippy 例外，保留其测试目的。
- 实测发现清理器在进程已退出时仍读取映像路径的竞态。现先检查退出状态，读取失败时做有界退出等待；活进程继续验证出生时间和映像，调用方仍确认生命周期锁释放。
- 朋友圈预览测试比较预期文件，不再在默认测试时覆盖受版本控制的 HTML；比较时兼容 LF/CRLF。
- 删除 ASR 缓存夹具中冗余的样本复制构建脚本，直接使用仓库合成样本，避免构建修改源码树或读取旧副本。
- MCP 模拟服务复用既有模块，避免重复包含生产权限实现；独立 CLI 集成测试复用夹具库的模拟服务，不扩大生产私有函数的可见性。
- 为 `asr-local` 和 `mcp-voice` 夹具纳入 Cargo.lock，使其能参与 `--locked` 检查。
- 增加 `.github/workflows/quality.yml`，普通分支提交、PR 和手动运行均执行 Windows 检查；包含格式、编译、严格 Clippy、根测试、npm 测试和独立夹具编译。
- `scripts/check-fixtures.ps1` 按现有矩阵处理 26 个夹具，额外检查加密测试工程；保留三项具名 integration 例外，显式启用两项 runtime feature。脚本保留逐项日志并汇总失败，不把 `test=false` 的库强行当作完整应用测试宿主。
- 独立 checkout 必须使用各自的构建目录。本轮发现另一项任务与此任务共用 target，同名 `wx.exe` 被覆盖，导致真实进程测试可能执行不对应的源码版本；最终验收必须从本任务专属目录重新构建，先前共享目录结果只作为诊断记录。
- 夹具检查脚本校验 `.checkout-owner`，拒绝另一个 checkout 的目录或归属不明的非空外置目录。默认使用本 checkout 的 target；需要外置时使用独占的新目录。该校验不替代直接运行 Cargo 时的目录隔离责任。

## 复杂度评估

Clippy 的认知复杂度用于定位控制流热点，不能单凭分数判断是否需要拆分模块。以下是在相同规则下的生产热点比较：

| 函数 | 修订前 | 修订后 |
| --- | ---: | ---: |
| daemon `dispatch` | 76 | 52 |
| `run_monitor` | 35 | 30 |
| `run_latency` | 35 | 31 |
| `write_export_with_publication` | 27 | 26 |

这四个函数仍超过默认阈值 25，不能宣称复杂度告警已清零。保留完整协议路由、观测循环和发布顺序具有可读性及行为验证价值，不为了达标切成彼此传递大量状态的小函数。后续应围绕独立业务责任继续提取，并以现有运行时契约回归验证。长度规则同样作为人工审查线索，不把大函数、大测试或大文件一律认定为缺陷。

业务层已经与微信表结构分离，主要缺口在边界维护而不是缺少新的框架。本轮没有再创建一套业务层，也没有把第三方算法改名后描述为原创。

## 保留事项

1. 四个生产复杂度热点仍需持续关注；较长的协议路由和发布流程不通过机械拆文件消除。
2. `toolkit` 中仍混有工作流和文件基础设施；跨层基础设施整理应以真实复用点为界，避免重复封装。
3. 旧密钥材料的保留清理、历史退出码，以及主数据库导出与 WAL 查询的新鲜度差异，属于迁移和接口契约问题，本轮不借改名隐式改变它们。
4. 独立夹具的编译范围与运行范围需要分别记录。根测试通过不自动代表全部独立 integration 已执行。
5. 新 npm scope 权限和实际包发布尚未验证；GitHub Actions 配置已加入，未声称远端流水线已运行成功。
