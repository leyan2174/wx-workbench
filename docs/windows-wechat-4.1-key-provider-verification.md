# Windows 微信 4.1.10+ 密钥导出验证记录

## 结论

已在 Windows 本机对微信 `4.1.12.26` 完成端到端验证。当前 `wx-cli` 可以从正在运行且已登录的新版本微信进程中读取数据库密钥，并解密 `db_storage` 下的消息数据库。

这次验证覆盖了完整链路：

1. 读取 `Weixin.exe` 文件版本。
2. 根据版本选择对应的密钥提供器。
3. 只读扫描微信进程内存中的 `Config.Cipher` 数据。
4. 使用数据库第一页的 SQLCipher HMAC 校验候选密钥。
5. 将已验证的数据库密钥写入本机 `all_keys.json`。
6. 跨消息数据库分片读取会话、历史消息和统计信息。

| 项目 | 实测值 |
| --- | --- |
| 平台 | Windows x64 |
| 微信进程 | `Weixin.exe` |
| 微信版本 | `4.1.12.26` |
| wx-cli | `0.3.0-leyan.1` 本地 release 构建 |
| 测试会话 | 本机已有群聊数据 |

不将密钥、原始数据库、账号目录或聊天内容提交到仓库。文中的会话名称仅用于说明验证命令，测试数据仍只保留在本机。

## 验证命令

微信保持运行并完成登录后，在 Windows PowerShell 中执行：

```powershell
wx init --force
wx sessions --json
wx history "七龙珠" --limit 100 --json
wx stats "七龙珠" --json
```

`wx init --force` 会重新扫描并验证数据库密钥。后续 `history` 和 `stats` 用于验证解密结果，而不是只检查密钥文件是否存在。

- 消息数据库的多个分片能够被实际解密和查询；
- `wx-cli` 的新版密钥提供器已经在集成后的命令行程序中生效。

## 新版本密钥获取原理

### 1. 先按微信文件版本选择路径

扫描开始时，程序先通过 Windows 进程 API 找到 `Weixin.exe`，读取进程映像路径，再读取 PE 文件中的 `VS_FIXEDFILEINFO` 版本资源。版本判断发生在扫描前，因此不会把新旧两套内存布局混在一起尝试。

当前阈值为 `4.1.10`：

- `4.1.9` 及更早版本继续使用旧的 raw-key 扫描器；
- `4.1.10` 及更新版本使用 `Config.Cipher` 扫描器。

### 2. 在微信进程中定位 `Config.Cipher`

新版微信不会像旧版本那样直接把可搜索的完整 `x'<key><salt>'` 字符串稳定地放在内存中。当前实现利用 WCDB 配置对象留下的字符串特征：

```text
com.Tencent.WCDB.Config.Cipher
```

程序使用 `VirtualQueryEx` 枚举微信进程中已提交且可读的内存区域，再通过 `ReadProcessMemory` 分块读取。找到上述字符串后，继续校验字符串对象的地址和长度，并沿对象引用找到 `Config.Cipher` 实例及其数据缓冲区。这样可以减少随机内存内容被误认为密钥材料的可能性。

### 3. 解码内存中的候选材料

`Config.Cipher` 对象中的数据不是最终数据库密钥，而是一个经过轻量变换的短数据块。当前版本中，该数据块经过固定 XOR 掩码还原后，包含类似下面的 WCDB 原始密钥材料：

```text
x'<64 个十六进制字符表示的 32 字节 key><32 个十六进制字符表示的 16 字节 salt>'
```

程序只接受符合结构的十六进制候选值，并从候选材料中提取 32 字节 raw key。这里的字符串特征和 XOR 解码规则属于当前微信构建的实现细节，不应假设在未来版本中永久不变。

### 4. 用数据库第一页验证候选 key

扫描内存得到的候选值不会直接写入密钥文件。程序会针对本机每个加密数据库读取第一页，并按微信 4.x 的 SQLCipher 参数进行 HMAC 校验：

1. 取数据库第一页前 16 字节作为 salt。
2. 将 salt 的每个字节与 `0x3a` 异或，得到 HMAC salt。
3. 使用候选 raw key 和该 HMAC salt 做 PBKDF2-HMAC-SHA512，迭代 2 次，得到 32 字节 MAC key。
4. 对第一页的加密内容、页码 `1` 计算 HMAC-SHA512。
5. 只有计算结果与数据库页尾保存的 HMAC 完全一致，才接受该候选 key。

微信 4.x 消息数据库使用 4096 字节页，第一页的 salt 是明文，页尾包含 IV 和 HMAC 保留区。实现还会优先检查当前 WAL 中对应的第一页，避免数据库主文件较旧时误判密钥。

因此，真正的验证标准不是“内存里找到了一段像 key 的十六进制字符串”，而是“候选 key 能通过数据库页级完整性校验，并能继续解密读取表内容”。

### 5. 完整匹配后才更新密钥文件

程序会将候选 key 与数据库 salt 建立对应关系，直到目标数据库全部完成校验才返回成功。新版路径没有旧方式回退：如果数据库没有全部验证通过，命令直接失败，已有 `all_keys.json` 不被新结果覆盖。

这套设计的作用是：

- 防止不同微信版本的内存结构被错误混用；
- 防止随机候选值污染密钥文件；
- 让 `history`、`stats` 等后续命令成为实际的解密验证，而不只是文件存在性检查。

### 6. 进程访问方式与边界

当前 Windows 实现只申请 `PROCESS_VM_READ` 和 `PROCESS_QUERY_INFORMATION` 权限，使用系统 API 读取进程内存，不注入 DLL、不写入微信进程内存，也不修改微信运行状态。但“只读”不等于对所有安全软件或微信版本完全不可感知，具体行为仍取决于操作系统、权限策略和微信后续更新。

## 版本选择策略

Windows 扫描器按 `Weixin.exe` 文件版本选择实现：

| 微信版本 | 密钥提供器 |
| --- | --- |
| `< 4.1.10` | 原有 legacy raw-key 扫描方式 |
| `>= 4.1.10` | `Config.Cipher` 只读扫描方式 |

新版扫描失败时不会尝试旧方式回退，而是直接退出，并保留已有密钥文件不变。这样可以避免新旧内存布局混用，也不会改变旧版本的原有路径。

新版扫描器只申请 `PROCESS_VM_READ` 和 `PROCESS_QUERY_INFORMATION` 权限，通过 `VirtualQueryEx` 枚举可读区域，再用 `ReadProcessMemory` 读取内容。当前实现不向微信进程注入代码，也不修改进程内存；这属于实现层面的只读保证，不代表能够对所有安全软件或微信版本承诺完全不可感知。

## 边界与后续验证

- 本次实测直接覆盖微信 `4.1.12.26`，不能据此保证所有 `4.1.10+` 小版本都具有相同内存布局。
- 微信必须在扫描时运行并完成登录；密钥扫描针对当前登录账号和当前机器。
- 图片、视频和语音的消息记录已经能够读取，但附件内容和语音转写需要单独执行附件解密或 ASR 流程。
- 不应将 `all_keys.json`、数据库文件或未脱敏聊天导出文件提交到 Git 仓库。
